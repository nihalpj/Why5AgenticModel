Qwen 3.5 4B ⟶ Why5 2B

How a small teacher's reasoning is distilled into an adaptive-depth agentic model — and what is deliberately not distilled.
response-based KD on-policy correction → DPO environment-as-judge rubric-supervised depth control

1 The big idea: split "5-why" into three targets

The 5-why principle looks like one behavior, but it's three separable learning problems. Only two of them should come from the teacher.

✗ not distilled

Depth routing — when to do 3, 4, or 5 whys

Comes from the factory rubric: a deterministic function of the task seed's features (call-graph size, branching, retry-reasoning). Labels are exact, and an FSM at serve time enforces the step count. If the student imitated the teacher here, it would inherit the teacher's miscalibration — so the depth token <|depth_N|> is CE-supervised by the rubric only and excluded from KL.

✓ distilled

Why-step content — the reasoning itself

The teacher supplies the text inside the why-steps: intent decomposition, information-gap analysis, tool mapping, contingency ordering, hypothesis revision. Sampled 4 candidates per seed, parsed to exactly N steps or rejected, median-length valid candidate kept (no verbosity bias).

✓ distilled + verified

Tool competence — calls, ordering, recovery

The teacher proposes; the sandbox disposes. Every tool call must validate against its JSON Schema (G3) and the whole trajectory must execute successfully in the sandbox (G4/G5) before the trace can enter the corpus. The teacher's errors never reach the student.

2 System architecture

Three bands: the teacher fleet supplies reasoning content, the data factory owns ground truth and verification, and the student stack trains, holds, and serves the Why5 2B model. The dashed purple return path is the on-policy loop.

3 Data pipeline — seed to training shard

Every token's journey: structured seed → teacher candidates → parse/median-select → ten gates → immutable JSONL shard → splits → the right consumer. Red exits are counted against the teacher; amber exits get one self-correction retry before the seed is re-qualified.

4 The five-stage pipeline (click a stage to expand)

Implemented in distill/why5_distill/ — every stage runs offline in mock mode: MOCK=1 ./run_distillation.sh.

Stage 0Teacher preparation & calibrationweek 1–2▶
Serve Qwen 3.5 4B on vLLM and run the format adapter: factory seeds → Hermes-style chat prompts; teacher output → parsed <why> blocks. A 2,000-seed calibration run measures per-tier gate pass rates: ≥ 60% acceptance on tiers 3–4 keeps the 4B as bulk teacher; tier-5 acceptance < 40% routes MAX-depth work to an escalation teacher (the 4B ceiling shows up on the hardest depth first).
  • why5_distill/teacher.py — adapter + parser, mock mode included
↓
Stage 1Bulk trace distillationweek 3–8▶
The factory generates the corpus with the teacher plugged into TraceGenerator. The seed's structure (depth, call graph, faults, distractor tools) is given; the teacher fills in why-content. Four candidates per seed → parse → median-select → all ten gates (G1–G10) → JSONL shard.
  • Tier quotas enforced at storage: 40 / 40 / 20 for depths 3/4/5
  • Teacher-vs-rubric routing disagreements are logged and audited — not silently kept or dropped
  • why5_distill/gen_corpus.py
↓
Stage 2Escalation for hard tracesweek 5–8▶
Gold-MAX (tier-5) seeds and all D5 counterfactual verification passes go to a larger same-family teacher. Budget-capped at ≤ 20% of teacher tokens — if it exceeds that, the tier-5 rubric itself is re-audited (are we over-injecting retry_reasoning?).
↓
Stage 3Student SFT on the distilled corpusweek 13–16▶
Standard SFT with protocol-aware loss masking: supervise only the depth token, why-steps, plan, tool-call arguments and final answer; mask system/user/tool-result spans. Two distillation- specific touches:
  • Anti-imitation upweight — no-tool/refusal traces get loss weight ×1.5 (small models under-generate refusal, and would inherit that bias)
  • Optional logit KD (--kd β) — forward KL on supervised positions only, never on protocol control tokens, so the teacher cannot soften the depth contract. Requires the Qwen tokenizer on the student (exact token-ID alignment)
  • why5_distill/sft_data.py + train_sft.py
↓
Stage 4On-policy correction → DPOweek 13–18▶
The highest-leverage step. The student rolls out on fresh held-out seeds; the sandbox judges (no teacher scoring → no bias, no reward-hacking surface); failures get a teacher-corrected trace for the same seed → (failed student, corrected teacher) DPO pairs. Teaching is aimed at exactly the states where this student actually errs.
  • why5_distill/on_policy.py + dpo_train.py

5 Anatomy of one distillation exchange

A real tier-4 seed from the factory — "Order 8830 failed to pay twice — diagnose it and issue a refund if allowed." Note what is not in the request: the gold call graph stays on the factory side as judging ground truth, and the depth (4) is dictated by the rubric, not asked of the teacher.

REQUEST → POST :8000/v1/chat/completions
{
  "model": "Qwen/Qwen3.5-4B",
  "messages": [
    { "role": "system", "content":
      "You MUST respond with exactly 4 why-steps
       inside <why>...</why> tags ..." },
    { "role": "user", "content":
      "Task: Order 8830 failed to pay twice ...

       Available tools:
       [ 12 JSON Schemas — 4 correct tools
         + 8 distractors with ambiguous
         names: get_record_by_id,
         shipment_entry, payroll_entry ]

       Reason in exactly 4 why-steps.
       Step focus: 1 intent · 2 gaps ·
       3 tool mapping · 4 ordering/risks" }
  ],
  "temperature": 0.7,
  "top_p": 0.95
}
RESPONSE ← teacher (vLLM)
{
  "choices": [{ "message": { "role": "assistant",
    "content": "
<why>1. What does the user actually need?
   Diagnosis of the double payment failure,
   refund only if policy allows it.</why>
<why>2. What information is missing? The order
   record, the payment-attempt log with
   failure codes, the policy verdict.</why>
<why>3. Which tools provide it? get_order,
   get_payment_log, check_refund_
   eligibility, create_refund.</why>
<why>4. What could fail / ordering? Later calls
   consume earlier outputs; refund must
   wait for the eligibility verdict.</why>" }}
  ],
  "usage": { "prompt_tokens": 1187,
             "completion_tokens": 214 }
}
What happens to this response: the parser accepts it only because it contains exactly 4 <why> blocks (G2). Of 4 sampled candidates, the median-length valid one is kept. The teacher's text is the only thing taken — the factory wraps it with its own depth token, plan, sandbox-verified tool calls with concrete resolved arguments, and final answer. A candidate with 3 or 5 steps is format-rejected and counts against the teacher's acceptance metric, never against the record.

6 The on-policy correction loop (Stage 4)

Where distillation stops being imitation. The student's own mistakes become the curriculum, and the environment — not the teacher — decides what a mistake is.

🎲
1 · Fresh seed

Held-out stream (rng seed 777), never seen in SFT. Depth forced to rubric gold.

🤖
2 · Student rollout

SFT checkpoint generates depth + whys + tool calls via its serve endpoint (:8001).

⚖️
3 · Sandbox judge

Parse (G1) → schema-valid args (G3) → executable trajectory (G4/G5). No teacher scoring.

❌
4 · On failure

Failure mode recorded: malformed JSON, schema mismatch, phantom tool, unexecutable order.

🧑‍🏫
5 · Teacher fix

Teacher regenerates for the same seed with the failure explanation appended → full gates.

⚖
6 · DPO pair

chosen = gate-clean teacher fix · rejected = the student's raw failed rollout (malformed parts kept as-is).

Yield gate: ≥ 50% of failed rollouts must yield a valid teacher correction — the pipeline warns below that (plan §7). Post-DPO, the student's repeat-failure rate on the same seeds should drop to ≤ 20% of its pre-DPO rate.
